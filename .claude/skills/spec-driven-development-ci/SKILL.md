# 非対話CIにおける仕様駆動開発フロー

## なぜこのスキルが必要か

CLAUDE.mdの仕様駆動開発ルールは「各フェーズは前フェーズの内容についてユーザーの承認を得てから次に進む」ことを求めるが、GitHub Actions上の`@claude`メンションは1回の非対話ターンで完結する必要があり、フェーズごとに人間との往復を待つことができない。このスキルは、その制約の中でCLAUDE.mdの意図（無許可での仕様変更を防ぐ）をできる限り保ちながら依頼を完遂するための、GitHub Actions向けの手順を定める。ローカルの対話セッションでは、このスキルではなく通常通り`/spec-init`等のフェーズごとの承認フローを使う。

## 適用対象

依頼内容が新機能の追加・既存機能の仕様変更を求めるものである場合に使う。また、起動元コメント本文だけでは自己完結した依頼に見えない短い返信（「進めてください」「OK」「それは違う、〜にして」等）であっても、`gh issue view`/`gh pr view`で確認した結果、過去にこのスキルがエスカレーションして投稿した提案への返信だと判断できる場合は、このスキルの「再開時の扱い」節に従う。以下は対象外（このスキルを使わず通常通り対応する）。

- 既存の実装が仕様通りに動いていないことの修正（バグ修正）のみを求める依頼
- 見た目・挙動の確認だけを求める依頼（`flutter-ui-android-verify-ci`/`flutter-ui-ios-verify-ci`へ進む）

判断に迷う場合（新機能なのかバグ修正なのか依頼文だけでは断定できない場合）は、このスキルを適用する側に倒す（3節の`spec-change-escalation-checker`が、結果的に影響の限定された小さな変更だと判定すれば自動進行するだけなので、過剰適用のコストは低い）。

## 手順

1. 依頼内容が`specs/`配下の追加・変更を必要とするか確認する。`Glob`/`Grep`で`specs/**/*.md`を探索し、依頼内容に対応する仕様（`requirements.md`）が既に存在し、かつ依頼内容をカバーしているかを確認する。
   - 既存仕様がすでに依頼内容をカバーしている場合（＝実質バグ修正）、このスキルの残りの手順は不要。通常通り実装のみ進める。
   - 対応する仕様が無い、または依頼内容が既存仕様を変更・拡張するものである場合、2節以降に進む。
2. Issueコメント由来の依頼で、まだ検証対象のブランチが無い場合は、`git checkout -b <branch-name>`で新規ブランチを作成する。ブランチ名は機能を表す短い英語（例: `feat/note-detail-map-pin`）にする。PRコメント由来で既にブランチがある場合はこの節は不要。
3. `spec-change-escalation-checker`agentを**同期的に（`run_in_background: false`を指定して）**呼び出し、依頼内容をそのまま渡す。**バックグラウンド（非同期）呼び出しは使わないこと**（非対話CIセッションには後続ターンが無く、非同期呼び出しの完了通知を受け取れないため）。
4. 応答のJSON中の`escalate`で分岐する。

### 4-a. `escalate: false`（影響が限定的な追加・削除）

そのまま自動で進める。

1. `specs/<feature-name>/`に`requirements.md`と`design.md`を作成・更新する（既存の`specs/`配下のディレクトリを参考に、同じ体裁で書く）。要件と設計を分けて人間の承認を待つことはできないため、1回のターンで両方書き上げる。`tasks.md`は作らない（段階的なタスク承認も非対話ターンでは行えないため、そのまま実装に進む）。
2. 作成した`requirements.md`/`design.md`を含めてコミットする（CLAUDE.mdの「`specs/`以下の仕様書はコードと同様にレビュー・コミット対象として扱う」方針に従う）。
3. 設計に基づいてFlutter/Dartの実装を行う。
4. 実装をコミットし、対象ブランチにpushする。
5. 通常の検証フロー（`android-emu-verify-dispatch`/`ios-sim-verify-dispatch`）に進む。

### 4-b. `escalate: true`（想定外の影響が懸念される追加・削除、または既存仕様との矛盾）

`specs/`配下のファイルは書き換えず、実装にも着手しない。

1. `requirements.md`/`design.md`相当の内容（何を・なぜ変更するのか、`spec-change-escalation-checker`が示した懸念点）をドラフトとして作成するが、コミットはしない。
2. このターンの最終応答（`gh pr comment`/`gh issue comment`）に、ドラフト内容と、`spec-change-escalation-checker`の`reason`（エスカレーション理由）をそのまま含める。「この提案に承認の返信をいただければ、次回の`@claude`メンションで実装まで進めます」という趣旨を明記する。
3. CLAUDE.mdの「進行中のチェックリストを更新しただけで終えてはならない」規則の例外（`claude-android.yaml`/`claude-ios.yaml`への引き継ぎ）はここには該当しない。通常通り、依頼のどこまでが完了し、何を人間に確認してほしいかを文章で明示した最終応答を残すこと。

## 再開時の扱い（エスカレーション後の返信）

起動元コメントへの返信が新たな`@claude`メンションとして届いた場合、それ単独では自己完結した依頼に見えない短い文面であっても、まず`gh issue view`/`gh pr view`等でコメント履歴を確認し、直前に自分（Claude）がこのスキルの4-b節で投稿した提案があるかを確認する。無ければ通常通りの依頼として扱う。あれば、返信内容を次のいずれかに分類して対応する。

- **承認**（例:「進めてください」「承認します」「OK」等の肯定的な返信）: 直前の提案内容をそのまま4-a節の手順で実行する（`spec-change-escalation-checker`を再度呼び出す必要は無い）。
- **却下**（例:「それはやらない」「やめて」等）: `specs/`・実装のどちらにも着手せず、依頼を取り下げたことを最終応答に明記して終了する。
- **修正指示**（例:「それは違う、〜にして」等、承認でも却下でもなく提案内容の変更を求めるもの）: 修正指示を踏まえて提案（ドラフトの`requirements.md`/`design.md`相当）を作り直し、4-b節の手順で再度エスカレーションする（再度`spec-change-escalation-checker`を呼び出し、修正後の内容で影響範囲を判定し直す）。
- **承認・却下・修正指示のいずれとも判断できない**: 無理に進めず、どう解釈すべきか分からなかった旨を明記した上で改めてエスカレーションする（4-b節）。
